# Configure traffic access

This guide explains how to route application traffic through Nagi and how to inspect the result. Start mihomo with a profile containing useful proxy nodes first; the default profile routes directly.

1. Run `nagi start` and `nagi ports status`. A mixed port accepts HTTP and SOCKS clients; the HTTP port accepts HTTP and HTTPS CONNECT clients. A port of `0` is disabled.
2. On macOS, to use OS proxy aware applications, run `nagi system-proxy enable`, then `nagi system-proxy status`. Nagi saves prior OS settings and restores them with `nagi system-proxy disable` or `nagi stop`. On Linux, configure each application to use the listener shown by `nagi ports status`.
3. For traffic that does not honor OS proxy settings, inspect `nagi tun status` and `nagi logs`. Newly created default profiles include TUN and DNS hijack settings but leave TUN disabled; run `nagi tun enable` to activate it. When the configuration names a TUN device, `adapter_status` reports whether its OS interface is missing, down, or up. TUN requires OS permission to create an adapter and install routes. On macOS, Nagi also saves network-service DNS settings and points them at the running TUN DNS endpoints. Run `nagi tun disable` to stop it and restore the saved DNS settings.
4. To allow other devices to connect to Nagi's proxy listener, run `nagi lan enable ADDRESS`, replacing ADDRESS with a local interface IP. `nagi lan enable` binds all interfaces; `nagi lan disable` returns to loopback. Check `nagi lan status` and configure your firewall before sharing a listener.

On macOS, check `nagi tun status` for `system_dns` as well as adapter state. DNS takeover requires an up TUN adapter, enabled mihomo DNS, and administrator access to network-service settings. If enable fails, inspect the reported rollback state and use the privileged helper described below. Stop, quit, and unexpected engine exit also restore the original static DNS or DHCP settings. An external edit is preserved and reported as a conflict; the restore journal remains until recovery succeeds. See the [traffic access reference](../reference/cli.md#traffic-access) for recovery and output fields.

System proxy settings route only apps that honor the OS HTTP/HTTPS proxy. TUN captures routed traffic through the adapter, subject to OS routes and permissions. An up TUN interface alone does not prove routes or DNS requests use it. Neither command guarantees that every app or DNS request uses a proxy. LAN access exposes a listener but does not change another device's routing. Use `nagi connections list` to inspect traffic seen by mihomo and `nagi logs` for adapter or listener errors.

On macOS, if ordinary-user mihomo logs `Connect: operation not permitted` when creating `utun`, use the privileged helper. Install root-owned Nagi and mihomo executables at `/usr/local/bin`, then run `nagi stop`, `sudo /usr/local/bin/nagi privileged-helper install`, `nagi privileged-helper enable`, `nagi start`, and `nagi tun enable`. Check `nagi privileged-helper status`, `nagi tun status`, and `nagi logs`. The helper accepts audited inline proxies, built-in plugins, and inline or HTTP providers. It copies file providers and proxy TLS file references from the selected profile tree into root-private snapshots. It rejects scripts, external controllers, arbitrary file references, and unsupported protocol options before root mihomo starts. This mode requires a mihomo build with the matching restricted configuration policy. To return to the user backend, run `nagi stop` and `nagi privileged-helper disable`. The [CLI reference](../reference/cli.md#traffic-access) defines the commands and status fields. The preference saved by `nagi tun enable` or `nagi tun disable` persists across engine restarts, configuration reloads, profile changes, and subscription updates. See the [traffic access reference](../reference/cli.md#traffic-access) for preference priority and profile-local DNS TUN conflicts. The Nagi build includes mihomo's `with_gvisor` tag; a separately installed mihomo must also include it if the profile selects the gVisor TUN stack.

System proxy changes use `networksetup` for active macOS network services. Nagi does not manage Linux desktop proxy settings; `nagi system-proxy` returns `system_proxy_error` on Linux. While the macOS login service is active, `nagi startup check` compares managed system proxy settings with its saved baseline and target. It reasserts settings that exactly reverted to the baseline, reports other changes without overwriting them, and reports new macOS network services as untracked. Run `nagi system-proxy disable` and then `nagi system-proxy enable` to include newly active services. If restoration fails, run `nagi system-proxy disable` again; Nagi keeps the saved settings until restoration succeeds.
