# Terminal menu design

**Status:** implemented.

This document describes `nagi menu` responsibilities, navigation, input lifecycle, and failure handling. The [CLI reference](../reference/cli.md#terminal-menu) defines numbers, effects, terminal requirements, and exit codes.

## Responsibility and command boundary

The menu is a line-oriented interface that preserves terminal scrollback. It owns input, forms, navigation, resource pagination, and presentation. Existing CLI commands own business operations, validation, persistence, and activation. The menu does not read profile files, call mihomo, or change OS settings directly. The CLI remains the complete interface for advanced arguments and automation.

`internal/command` rejects `--json menu` and nonterminal input/output before starting a session. The menu runner invokes ordinary commands with `--json` and decodes their existing result envelope. The menu presentation adapter accepts command arguments and result data, renders readable state and bounded lists, and preserves raw configuration and logs. Ordinary CLI wording, JSON fields, syntax, and exit codes are unchanged; terminal status colors are shared with the ordinary CLI output layer.

The Network Access page batches independent `tun status`, `ports status`, `lan status`, and (on macOS) `system-proxy status` reads through the optional `ReadRunner` interface. The production command runner executes these reads concurrently with separate JSON output buffers and returns results in request order. Runners implementing only `Runner` retain serial reads. Page context is assembled after all results arrive, preserving summary order and each read's unknown/error state. Worker goroutines do not render, queue feedback, read input, or dispatch mutations. All operation flows remain sequential; a selected action still executes once, and its completion precedes the page reload. Start at Login uses one `startup status` read for login enablement and engine state. It shows only the applicable enable/disable action, omitting the toggle when enablement cannot be read. Enabling delegates automatic installation to `startup enable`; disabling delegates next-login preference changes to `startup disable` and keeps the current monitor and engine running. View details retains the full service and engine output, and service removal is under Advanced options with its interruption and data-preservation effects stated beside the action.

Most commands run in process. The session shows the result or error without echoing internal command arguments. An ordinary operation already submitted can finish; input cancellation does not imply cancellation or rollback of the business operation. Log following and traffic watching use a child Nagi process with a cancelable context. Ctrl-C cancels that stream and returns to the same page. User-mode mihomo runs in a separate process group, so canceling a stream does not stop it.

## Menu presentation

The session owns a semantic style renderer for menu UI text and uses `internal/output` for shared state-value colors. It detects terminal styling once from its output terminal and environment; the [CLI reference](../reference/cli.md#terminal-menu) defines the enable conditions and style meanings. Plain output retains the same wording, numeric mapping, and selected markers. `Item.Selected` carries actual node or profile selection state, independently of label text; rendering does not infer selection from names or status strings.

Titles, choice labels, action effects, feedback, and state values in page context and operation results have separate style roles. The home title `Nagi menu` is bold bright cyan; other page titles remain yellow. The renderer styles labels after the unstyled numeric prefix and dims effects separately, preserving the distinction between an operation and its explanation. Context keeps field labels and explanatory text in the terminal default. It colors selected profile values and recognized state values by meaning: positive states green, warning or unknown states yellow, errors red, and neutral mode/state values bright blue. Form editing and resubmission entries use the same label style. Numbers, page counts, zero-choice navigation, and input prompts retain the terminal default.

The renderer redacts menu labels, context, impacts, and feedback before applying styles. Feedback retains its success, warning, or error class while queued, then renders after the reloaded page and before its prompt. Partial completion and input validation use the warning class; command and read failures use the error class. Each styled span resets immediately, so plain prompts, user input, and subsequent output do not inherit menu styles.

Requested configuration, overrides, profile comparisons, recent logs, and child log or traffic streams bypass menu styling. The Enter-to-return prompt also remains plain. Styling changes no command wording, JSON contracts, business operations, or mihomo behavior.

## Page inventory

The home page shows mihomo state and the selected profile. Failed reads show unknown/unavailable state without hiding controls.

The [CLI reference page inventory](../reference/cli.md#terminal-menu) defines the eight home entries and their operation order: Service, Network Access, Proxies, Routing & DNS, Profiles & Subscriptions, Rewrite & Capture, Monitoring & Diagnostics, and Maintenance. Common actions lead each page; deletion is last. Profiles keeps Import a profile as a fixed action after the visible profile list, before pagination entries. It remains available on every page, when the list is empty, and after a failed profile read clears resource choices. Current Configuration is a sibling of Profiles and Subscriptions and operates on the selected profile through the existing show, validate, and reload commands, in that order. Backup & Restore, Local Overrides, DNS, routing rules, and login startup group their related operations in dedicated pages.

Proxies separates Proxy Groups, Proxy Providers, and Tailscale. Routing & DNS contains Proxy Mode, Routing Rules, and DNS. Rewrite & Capture separates Request Rewrite, Request Capture, and Certificate Authority so capture and shared certificate/trust operations are reachable independently of rewrite-rule management.

Monitoring & Diagnostics contains Connections, Traffic, Logs, Basic checks, Detailed diagnostics, and Export diagnostics, in that order. Traffic contains Watch traffic; Logs contains Show recent logs and Follow logs. Brief page guidance explains observation and checks without invoking commands automatically. Service exposes lifecycle operations directly, followed by Start at Login, Startup Recovery, and Privileged helper on macOS. Startup Recovery contains Repair startup state (`startup check`) and Clean stale runtime records (`recover`). The helper page retains runtime-backend selection and helper management. Maintenance contains version, update, App installation/removal on macOS, and uninstall variants.

System Proxy, TUN, and LAN Access place their explicit enable and disable actions before details, in that order. Both actions remain available independently of the displayed state; the menu does not substitute a toggle or infer permission to mutate from a status read. The parent traffic summaries, concurrent reads, Listener Ports, and platform-specific pages retain their existing behavior. Command implementations continue to own permissions, persistence, activation, and restoration.

`settings_summary.go` adapts typed command results for Network Access, its settings pages, DNS, and Privileged helper. It selects the fields relevant to each page and renders semantic state rather than nested field labels. DNS's `tun_enabled` field describes TUN configuration, not verified DNS capture. Helper summaries read the nested service installation/activity fields and `selected_backend`. Missing, null, or malformed values remain unknown independently, and failed reads retain their diagnostic. The [CLI reference](../reference/cli.md#terminal-menu) defines the displayed summary contract. Detail actions retain full results, and these adapters issue no additional reads or mutations.

Profile Local Overrides includes **Apply default runtime settings** (or **Disable default runtime settings** while applied), a state-aware action that applies safe settings from the default profile and restores the previous override when selected again. It gets the target profile's DNS proxy requirement, eligible groups, and saved group from `profile override default-status NAME`. If a group is required on first apply, the menu asks the user to select one and passes it to `profile override apply-default NAME --dns-proxy GROUP`. A later apply reuses the saved group without prompting; if that group is no longer eligible, the menu asks for a replacement. A profile without proxy nodes applies defaults without a group. The CLI remains responsible for group validation, persistence, and activation. Completion and cross-group search are available through ordinary commands only. Local Overrides reads default runtime settings state in its own page loader on entry and after every operation, rebuilding its action label, selection marker, and DNS group explanation. A failed status read hides the default-settings toggle while retaining show, set, and clear actions. Before applying or restoring defaults, the menu rereads state; if it differs from the displayed action, no mutation is dispatched and the refreshed page asks the user to choose again.

The menu does not expose every command argument variant; per-group latency URL settings and one-off test URL and timeout arguments remain available through ordinary commands. DNS checks inspect configuration and mihomo's API without claiming system-wide DNS leak verification.

## Input and page state

A session owns a single buffered reader. Terminal reads wait for canonical input using platform readiness polling in the same goroutine, checking already buffered data first. There are no per-prompt reading goroutines left behind after cancellation. The session receives interrupt signals while active; completed commands and streams discard their consumed interrupt signals before returning to input.

Each stack frame keeps its page, latest view, page index, and redraw state. A view separates resources (`Items`) from operations (`Actions`) internally so only resources paginate. `numberedChoices` produces the shared mapping for both rendering and dispatch: up to ten resources, all actions, then available pagination entries. Selectors use the same mapping. There is no letter-key allocation for actions or filter state; entering `q` at a numeric choice exits the menu without displaying a hint.

A view reloads on entry, operation completion, and return from a child. Pagination renders the existing snapshot without reading again. Page indices clamp to the last valid page after reload. Blank and invalid choices leave the rendered page intact and repeat the prompt. Zero returns, cancels a selector, or exits at home. Help, refresh, filtering, and search have no menu entries.

The session queues command results until the refreshed page has rendered, then prints them immediately before the next prompt. Failed forms flush feedback after their numeric editing/submission choices. Raw configuration, overrides, profile comparisons, and recent logs are shown before an Enter-to-return prompt; only then does the page reload. Streams write directly until cancellation.

An item can open a child, dispatch existing command arguments, run a custom flow, or return a navigation result. Navigation results distinguish staying and refreshing, opening a detail page, and returning to the parent. They take effect only after a successful flow.

Text prompts accept `0`, `b`, and `q` as literal content. Ctrl-C cancels the current form and returns to its page; during page selection it returns to the parent, or exits at home. EOF exits. Forms validate fields as entered and retain other values. After a failed command, users can edit a field and explicitly resubmit using numbered entries, or cancel with zero. There is no automatic retry of mutations and no second confirmation; operation effects are displayed beside entries.

## Proxy flow

Selecting Proxies → Proxy Groups loads groups, including current nodes. Selecting a group opens its node list. Selecting a node dispatches `proxy select GROUP NODE` once, then refreshes the current marker while staying in the list. Names containing spaces remain one argument. The ordinary path takes four selections from home.

If the group read fails, Proxy Groups queries the existing `status` command, clears resource choices, and directs recovery through Service. Recovery guidance distinguishes a stopped engine, an unexpected exit with stale records, a running process, and unknown status. A known stopped engine shows its status-specific recovery guidance without the generic read-error line; other failures preserve the original group-read error. The menu does not infer that a running process has a reachable controller. The shared page runner uses a page's `ReadErrorHint` for failed reads when provided, otherwise its generic unavailable message. Reopening Proxies → Proxy Groups after using Service triggers the ordinary group reload; no lifecycle command or retry runs automatically.

The provider entry lists redacted names and node counts. Opening a provider and every read after an operation call `proxy provider show NAME`; update and healthcheck actions use their corresponding CLI commands. A failed provider read clears selectable nodes while leaving those actions available for recovery. Delete provider invokes `proxy provider remove NAME` once and returns to the list only on success; failures remain on the details page.

The provider list always offers Add provider, including when empty or unreadable. Its shared form collects the provider name, HTTP(S) URL, existing or new group name, update interval, and optional test URL, then calls `proxy provider add`. Submission errors retain the form values for explicit editing and retry. The form briefly describes saving and reload; successful creation of a new group reports its DIRECT selection and unchanged routing rules. Configuration persistence and activation remain CLI responsibilities; the menu does not require a successful live group read to add a provider while stopped.

Details, latency tests, restoring saved choices, and returning an automatic group to automatic selection are fixed actions. Ordinary nodes and latency-ranked nodes all switch with the same numeric action. Node lists use CLI `node_info` to distinguish entries, and `node_delays` for ordinary nodes without initiating tests. Successful zero milliseconds displays `<1 ms`. Nested groups keep their names and selected markers, with optional availability from the current selected leaf; they have no own latency. DIRECT and REJECT keep only their names and selected markers. Individual node-test choices exclude built-ins, nested groups, and unresolved identities; they dispatch `proxy test group GROUP NODE` or `proxy test provider PROVIDER NODE`, retaining source context and configured test conditions. A group page retains batch ordering across selections and refreshes, but current engine measurements take precedence over older page values, including a newer failure. Removed nodes lose their page measurements. Group and provider details show measurement times and sanitized test origins. Automatic groups show fixed or automatic state. Latency actions disclose possible release of a fixed choice and preserve underlying errors about partial completion or unknown state.

Subscription and Provider detail pages offer **Automatic latency checks**; group pages keep manual tests and selection controls. This child page reads `proxy healthcheck show` on entry and displays the selected profile, interval, sanitized test URL, their sources, enabled/lazy settings, and scheduling caveats. Retained forms call the interval and URL set commands; independent reset actions restore each inherited value. Subscription and Provider detail pages also edit their separate download update intervals. New subscription and Provider forms accept an optional test URL, and new subscriptions accept a download interval before the first apply. Reading settings never probes nodes. Forms retain input after validation or command failure for explicit retry. Configuration persistence, validation, reload, and recovery belong to the CLI. Group URL and interval edits remain in the CLI; see the [latency settings contract](../reference/cli.md#automatic-latency-check-intervals).

### Node and chain flows

Proxies lists **Proxy Groups**, **Node Management**, **Node Chains**, and **Proxy Providers**, in that order. Node and chain pages read selected-profile effective configuration through `proxy node` and `proxy chain`, including while the engine is stopped. The menu owns only navigation, retained drafts, and presentation; CLI validation, persistence, dependency analysis, activation, and recovery remain authoritative. The native macOS App is unchanged.

Node Management lists applied subscription nodes first, provider entries next, and other top-level nodes last, using the ordering and source metadata returned by [`proxy node list`](../reference/cli.md#proxy-nodes-and-chains). Provider entries open the existing provider detail page, whose node list preserves mihomo's payload order. The list and provider entries remain readable while the engine is stopped; opening provider details requires its running API. Top-level nodes show their names and types. Details, group membership, and chain controls are available for every type; protocol add/edit/remove forms currently support Tailscale only. Creation first selects zero or more groups with numeric toggles and pagination, then collects the Tailscale fields. One submission sends repeated `--group` arguments, making node creation and membership changes atomic. Group editing replaces the complete explicit membership set, while details distinguish automatic inclusion and exclusions. Pasted Auth Keys are visible, retained after a failed form submission, and passed through a private command stdin reader with `--auth-key-stdin`; they never become command arguments or standalone temporary key files. A blank edit key preserves the existing key. Cancellation or EOF before submission sends no mutation.

Node Chains chooses node, provider, or subscription scope, then a numeric multi-selection of targets. Subscription scope uses actual records associated with the selected profile. A shared draft appends hops in traffic order and can remove the last hop; no protocol-specific bind page remains. The menu requests a dry-run plan and displays complete paths, edge replacements, shared use, and conflicts. Conflicting plans offer return to editing without Submit. An empty pending hop list previews target-chain clearing. Submit commits once without a second confirmation. A command failure retains the draft on the preview page for explicit retry; mutations are never retried automatically.

All selectors use standard numeric pagination and cancellation. Failed reads hide stale choices. Provider effects disclose all current and future payload nodes; subscription effects disclose persistence across explicit and scheduled application. Feedback reports configuration saving and any confirmed reload, without inferring Tailscale login or network success. See the [CLI contract](../reference/cli.md#proxy-nodes-and-chains) and [guide](../guides/proxy-nodes-and-chains.md).

## Request rewrite flow

Rewrite & Capture includes **Request Rewrite**. The page reads `request-rewrite status` and distinguishes saved intent, actual state, nullable TUN/service evidence, configured/active versions, generation, engine epoch, CA/trust and recovery. Enable is absent unless actual TUN is confirmed running; the page explains the reason. Enable and the ordinary disable action reread status and refuse to act on a changed selected profile. The recovery page retains an explicitly selected-profile disable action even when status is unavailable. Stored validation remains accessible; if the status snapshot has no profile, the selected profile is obtained through `profile list` and then passed explicitly as `--profile NAME`. Enabling does not start TUN or generate/trust a CA.

Child pages bind their script/rule/import/export/validate/preview commands to the profile name captured on entry, using explicit `--profile NAME`. Script and rule detail pages reload CLI summaries after operations. Failed reads expose no stale resources or state-dependent actions; the rewrite root retains Recovery, the parent retains Request Capture and Certificate Authority, and list pages retain Add. The menu owns only forms and presentation; CLI validation, storage, activation and recovery remain authoritative. Enabled rule domains define interception scope.

Local Scripts supports list, explicit sensitive source display/edit, add and removal. Ordinary pages show only ID, body access, source size and referencing rules. Editing explicitly requests `scripts source ID`; source stays in the retained form and is never included in ordinary summaries. The complete `{id,body_access,source}` JSON form accepts escaped newlines; private document import also supports multiline source. Removal uses CLI reference protection for enabled and disabled rules.

Ordered Rules supports add, explicit sensitive edit, enable/disable, removal and moving a rule to a numeric position. Moving submits the complete ordered ID array through stdin. A rule draft has matching/behavior, ordered operations and destination-consent pages, plus **Edit complete rule JSON**. The JSON route covers all four stages, every match predicate, `range_mode`, operation parameters and message-type selectors. Basic matching edits preserve other predicates. Operation forms cover every v2 kind; detailed JSON forms handle the additional operations. Operations can be edited, moved and removed; moving returns to the list before another edit. Existing values are retained when a field is left blank. Dedicated **Use root JSON pointer** and **Set empty value** draft actions explicitly clear supported optional values. JSON values preserve original number tokens. Destination consent has domain, schemes and ports; destination domains require enabled rule interception scope.

All rule subpages modify one in-memory draft. **Save rule** is the sole CLI mutation; Back, cancellation or EOF before Save leaves persisted rules unchanged. CLI failures retain that draft for editing and explicit Save again. Other rewrite forms that submit CLI operations display an initial numeric **Submit** after the last field; cancellation/EOF before it sends no command. Failed submissions retain fields and offer explicit Submit again, without automatic mutation retries or a second confirmation dialog. Local draft-field editing reuses the ordinary form lifecycle.

Ordinary rule summaries never contain operation values. Selecting **Edit rule** explicitly loads a portable CLI export into memory, validates the complete v2 document and selected rule ID, then opens that draft without displaying the full document. The optional `RawRunner` permits only request-rewrite document/public-CA exports; production raw dispatch omits `--json`, which those exports reject. File exports show brief completion feedback. Secret-bearing mutations use `InputRunner` with JSON on stdin, never JSON arguments or temporary files. No menu path reads storage or CA files directly.

Preview provides a structured request sample form, a complete staged-envelope JSON form and a private fixture-file path. The latter two support request, response, exchange and both WebSocket directions; the sample form submits a request-stage envelope. Each route displays its sensitive result only after explicit submission. The action discloses sensitive terminal scrollback, no network/DNS activity and no persistence; its result bypasses ordinary summary formatting and pauses before returning. Validation supports the stored document or a private input file. Import/export use CLI file operations. The sibling Certificate Authority page separates status, explicit generation and public-certificate file export. macOS additionally offers explicit login-keychain trust install/remove; Linux shows manual distribution/application trust instructions. Human CA validity times omit seconds. The [CLI contract](../reference/cli.md#tun-request-rewrite) remains authoritative for schemas, prerequisites, trust behavior and sensitive file requirements.

Closing or exiting the menu leaves mihomo and the rewrite service running. OS TUN interception and native macOS trust acceptance require their own platform checks; a Linux PTY journey does not establish those results.

## Rule import and management flow

Routing Rules offers one Import rules action. The retained form collects only a name and local path or HTTP(S) URL. Native rules retain their individual targets and order; there is no format selector or common-target prompt. Submission dispatches `rules import NAME SOURCE` once. Failed submissions keep form values for explicit editing or retry; form cancellation, interruption, or EOF before submission performs no mutation. The CLI owns reading/downloading, validation, snapshot persistence, and activation.

View Rules includes custom rules and sets. Manage Rules and Sets lists all named single rules, full-rule imports, and previously imported provider sets for enable, disable, and removal. Removal discloses that the entire named object is deleted; no individual imported-rule editing flow is provided. The [rule import reference](../reference/cli.md#rule-file-imports) defines input formats and dependencies.

## Rule test flow

Routing Rules offers Test Rule before its inspection, management, and import actions. The form validates a bare domain/IP, then submits `rules test TARGET` once using TCP port 443. The CLI sends synthetic metadata to mihomo's native rule test endpoint; the menu neither matches rules nor accesses providers directly. It renders the matched rule and outbound target with the reported limitations. A failed API request retains the input for numeric editing or explicit retry. EOF or interruption before submission sends no request. The [CLI reference](../reference/cli.md#destination-rule-tests) defines engine compatibility, optional metadata, DNS behavior, mode handling, and result fields.

## Subscription and profile flows

Add and Apply subscription saves the record, downloads its cache, and applies it through the existing commands in that order, then opens its detail page. Update and Apply downloads and then applies an existing subscription. A failed download prevents apply; a newly saved record remains available in the detail page. A failed apply keeps the new cache. Creation forms retry only the add stage; later failures never resubmit add. Encrypted feeds can be retried by setting an identity file in Encryption Settings and choosing Update and Apply.

Details show available update time, quota, and expiry, with missing metadata explicitly unknown. Subscription time and byte formatting belongs to the menu presentation adapter; the [CLI reference](../reference/cli.md#terminal-menu) defines its display rules. Quota comes from the latest provider response metadata rather than live mihomo traffic. Daily pages do not request previews or display change counts or lists; ordinary subscription preview, update, and apply commands remain available.

The combined action discloses that applying updates the target source configuration, retains local settings and node/group changes and any persistent subscription chain policy, and clears saved selections. Existing command validation and the apply transaction remain authoritative. The flow does not implicitly start mihomo or enable traffic access. Feedback states successful completion or the failed stage and its known resulting state, without dumping command metadata.

Automatic Updates and Encryption Settings read the named subscription from `subscription list` on entry and after operations. Automatic Updates shows the download interval or disabled state, retaining Set update interval and showing Disable automatic updates only when enabled. Encryption Settings shows only identity presence, offers Set or Replace identity file, and shows Clear encryption key only when configured. Neither identity content nor its stored path is displayed. Failed reads or missing records show unavailable state, preserve the setting action, and hide disable/clear actions.

Successful removal returns to the parent list; failure stays in detail. Profile imports and other multi-field flows reuse retained-value forms. Profile removal discloses deletion of configuration, backups, local overrides, and saved proxy choices while keeping subscriptions. The CLI owns cleanup and selected-profile protection; see [profile removal](../reference/cli.md#profile-removal).

## Failure handling and verification

Maintenance is available on macOS and Linux. Both platforms dispatch `version`,
`update`, and `uninstall` from the same page. macOS also shows menu bar App
install/removal actions; its separate privileged helper page is under Service.
Linux does not show macOS-only operations. Show version appears first, followed
by Update Nagi, on macOS Install menu bar App and Uninstall menu bar App, then
Uninstall Nagi and Uninstall Nagi and clear user data. Nagi uninstall offers
data-preserving removal and `uninstall --purge-data` to remove user data; effects
disclose what is removed. The menu does not download or install files itself;
the [maintenance design](installation.md) defines those operations.

Failed reads replace old resources, preventing selection of stale targets. Views can retain fixed recovery actions and state unknown/unavailable explicitly. Command failures display existing messages and known resulting state; the menu never infers successful saving, activation, or rollback. URLs in errors, page context, and list labels are redacted. Raw requested configuration and log content retain their ordinary command content.

Known profile, provider, DNS, and rule mutations show short completion messages rather than command metadata. Export destinations, requested details, diagnostics, and errors retain their detailed output. DNS child pages show only relevant state instead of repeating the full DNS summary. Maintenance and helper actions use brief effects while retaining data removal and process-stop prerequisites.

Action failures leave the menu usable and do not determine its exit status. Ordinary exit is `0`; unrecoverable input errors return `1`. Terminal/usage rejection returns `2` as defined in the reference.

Framework and feature tests inject runners to verify dispatch, numeric navigation, pagination, retained forms, navigation, bounded results, redaction, and stale-resource invalidation. Ordinary command tests remain authoritative for persistence, activation, and mihomo effects. Real PTY checks cover repeated interruption, buffered input, EOF, and stream return while mihomo remains running. Darwin cross-compilation checks compilation only; Linux PTY results do not establish macOS runtime acceptance.

The October 2026 verification passed the Go and menu tests, Linux PTY journeys (three-selection proxy switching with spaces, repeated form cancellation, literal text including zero, both streams, EOF, and exit without stopping mihomo), and Darwin source compilation. The final locked mihomo source was separately built and exercised through focused engine regression and isolated Nagi runtime checks. Full mihomo package testing remains limited by the documented listener/inbound timeout and offline nested dependencies. macOS menu-bar interactive acceptance still requires a macOS host.

The T6 request-rewrite menu verification passed injected-runner journeys, menu race tests, the full Go suite, Darwin ARM64 cross-compilation and an isolated Linux PTY journey under an ordinary UID. The PTY used a freshly built compatible engine from source commit `d7c0a70776e4e698bee43f2044e7fa91d2d67d7b` through the existing runtime override, with the release lock unchanged. It covered domain/rule CRUD and failure recovery, all operation forms and ordering, destination consent, sensitive preview/import/export, CA/public export, repeated interruption, EOF before Submit and menu exit while the engine remained running. TUN was disabled: enable correctly refused with `rewrite_tun_required`. No live interception, rewrite-child persistence or macOS trust result is claimed by those menu checks. Private fixture CA/configuration files were removed after verification.

## Localization

A session owns an immutable English or Simplified Chinese language context.
`NewSessionWithLanguage` binds it to page factories, forms and feedback; the
CLI passes the invocation context into `Run`. The production runner copies its
language per session and prefixes child reads, operations and streams with
`--lang`, keeping submitted business arguments unchanged. Concurrent reads never
mutate a global language preference.

Stable page/item identities and protocol values drive navigation and styling.
Translated labels never determine root navigation, selection or severity.
Optional message descriptors render existing string targets by exact JSON
Pointer; invalid metadata preserves original text and never mutates result data.
Requested raw configuration, logs, diffs, exports, capture values and child stream
bytes bypass descriptor substitution. See the [localization design](localization.md)
for the catalog, fallback and acceptance contract.
