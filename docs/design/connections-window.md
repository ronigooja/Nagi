# macOS Connections window

This document describes the implemented macOS 13+ Connections window, its in-memory observation history, CLI boundary, lifecycle and failure states. The short-connection changes compile and pass Connections tests on macOS; manual desktop acceptance remains outstanding. See the [App guide](../../macos/NagiApp/README.md#active-connections) and [CLI reference](../reference/cli.md#proxy-latency-connections-and-mode).

## Responsibilities and interfaces

mihomo owns connection tracking, rules, counters and closure. The CLI uses the pinned engine's `/connections` WebSocket with a millisecond interval for ordinary backends. Privileged backends sequentially read complete snapshots through the existing authenticated helper GET interface, without a helper protocol change. Both deliver an immediate first snapshot. The App runs one `nagi --json connections watch` child while the window is visible; the unified watch envelope may include `connections`, `failure_events` (or `failures`) and `gaps`. Failure records are diagnostic, non-closeable observations; gaps mark retained data interrupted. Closure uses `connections close ID` or `connections close-all`. It never calls mihomo or reads runtime files directly.

The CLI defaults to 250 ms sampling. Connections entirely between samples may be missed. Each successful NDJSON envelope contains the existing connection array and a machine-readable RFC3339Nano `sampled_at`. Human times use minute precision. Complete engine snapshots are limited to 4 MiB; the App limits each CLI stdout line to 8 MiB and stderr to 1 MiB. Oversized data fails explicitly without truncation.

The worker decodes each typed snapshot, then awaits sequential merging before reading the next line. Intermediate snapshots are not discarded. Merge and search/sort work runs outside the main actor. Table publication is coalesced to at most once per 500 ms during collection. User search, sorting, freeze and resume can update the view immediately.

## Observations and display

Successful snapshots merge by ID. An observed ID absent from the next successful snapshot becomes recently ended with its last observed fields. Reappearing IDs return to active state without duplication. Failure, cancellation and hidden windows never directly infer an end. Observation gaps mark retained records and selected details; data from those gaps cannot be recovered. Ended details explain that status is inferred, counters are last observed values, and exact end time and final traffic are unavailable.

History is memory-only: retain ended entries for five minutes from first observed disappearance, up to 1000 entries and a 32 MiB canonical JSON encoded-data budget. Evict oldest disappearance first, with ID breaking ties. Active snapshots remain complete. Expiry runs on merge, publication, visible-window timer ticks and reopening; expired entries are removed on resume from a frozen display. The selected detail is retained independently after eviction until selection changes or is cleared. Engine stop clears records, selection and freeze state.

The default filter is All, with Active, Recently Ended and Failed alternatives, a status column and separate active/ended counts. Failed records are bounded by the same five-minute/count retention and deduplicated by ID; a later failure replaces the record without changing active order. Active rows initially use newest-observed-first order: IDs first seen, or seen again after becoming ended, are placed above existing active IDs, while existing active IDs retain their relative order. The first snapshot's order is retained for its initial active IDs. Clicking a table column switches to that column's ascending or descending sort and keeps the user's choice across later snapshots; the live observation order is used again only for a new window model. Existing search fields, deterministic sorting, selection by ID and scroll anchoring remain. Ended and failed selections cannot be closed. Freeze Display fixes the published records, counters and selected values while collection and history merging continue. Search, sorting and selection operate on that fixed display. Resume Live publishes current records. Refresh and all close actions are disabled while frozen.

The AppKit controller retains a reusable resizable window with shared `NativeWindowLayout` screen fitting. The preferred frame is 1040 × 700 points and preferred minimum is 800 × 550. Table/detail panes scroll and can shrink on smaller screens. The toolbar holds search, filter, refresh and freeze; counts and last-update time occupy a separate summary row.

## Lifecycle and failures

Opening starts collection immediately. Window close, minimization, hiding, App hiding, sleep and quit invalidate the generation, exit freeze and cancel the child. Callers wait for real process exit and pipe draining before a replacement read or operation. Termination has bounded kill escalation. Old-generation results cannot replace current state. Reopening retains unexpired history and starts a fresh immediate stream. Explicit window-ordering hooks complement AppKit notifications; the existing cancellable minimization fallback remains.

Ordinary failures retain old data as stale and disable closure. Retry delays are 1, 2, 4, 8 and then 10 seconds, reset by a successful sample; the scheduling timer checks the retry deadline without creating overlapping children. Overflow pauses automatic retry until manual Refresh. Status unavailability suspends collection without inferring engine stop. Confirmed stop clears this session's observations.

## Closure and settings coordination

Capture the selected ID and submit each close once. Close All confirmation explains full scope beyond filtering and automatic reconnection. Before dispatch, cancel collection and await process exit; settings and quit use the existing gate and also wait for already submitted close requests. Failures and timeouts are never automatically resubmitted. Completion resumes collection only when eligible. Successful closure means request acceptance, including an already absent ID; no closed count is inferred. Reads do not animate the settings status icon or refresh the menu.

## Verification scope

Go tests cover WebSocket and helper bridge snapshots, interval validation, immediate/empty samples, NDJSON, response limits, cancellation, output errors, completion and runtime-independent help. Swift tests cover decoding, deterministic rows, disappearance/revival, history budgets/expiry, retained selection, intermediate samples while frozen, resume, stale/overflow behavior, cancellation and operation coordination.

Linux checks pass: `go test -p=1 ./...`, connection watch race tests, relative link targets and `git diff --check`. An initial parallel full-suite run hit the documented rewrite-script throughput timeout; the serial rerun passed.

macOS verification used a separate source copy over SSH, leaving the existing development checkout intact. Swift 6.0.3 compilation and `make build app` passed. With process-local `-AppleLanguages '(en)' -AppleLocale en_US`, all 18 Connections model/client tests and 8 window tests passed. The native fixture clicks Freeze/Resume and filters, verifies collection while frozen, checks disabled actions and minimum-window button bounds in Aqua/Dark Aqua, and retains the existing selection, sorting, scroll and visibility checks. A long-line framing slowdown found during native tests was fixed by searching only newly received bytes; the 8 MiB overflow test then completed in approximately 0.15 seconds.

The full English XCTest run executed 242 tests: one live-capture fixture skipped because no isolated live CLI was prepared, and one Request Rewrite layout assertion failed (`RequestRewriteWindowTests.testLongContentAndTabChangesDoNotGrowWindowOrPreventShrinking`, 157.5 versus 141.75 points with a 3-point tolerance). That assertion also failed when run alone; it remains outside this Connections change. Initial system-language runs were Chinese and failed English-only assertions, so language was constrained only for test processes. Cached view screenshots were generated for both appearances, but their rendering is incomplete and does not establish desktop visual acceptance. Manual light/dark rendering and physical mouse/keyboard acceptance remain outstanding.
