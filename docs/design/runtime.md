# Runtime and configuration design

This document describes the implemented process and configuration flow. The CLI is the only control layer used by the macOS app.

Profile-store validation runs mihomo as a child process with a 120-second deadline and the caller's context, using a private temporary YAML file beside the source profiles. Cancellation or timeout stops the child and removes the temporary configuration. Subscription replacement validates its complete rebased effective candidate before writing source or overrides, then commits without repeating source-only or managed-policy validation in `Apply`. Materialization still validates any generated activation configuration. Each subprocess has its own deadline; download, configuration-lock waits, activation, and recovery are separate steps. Mihomo owns any missing GeoIP/GeoSite database downloads performed during parsing. Timeout and cancellation use fixed diagnostics without exposing configuration contents; other structured validation diagnostics retain their existing behavior.

On macOS, data lives under `~/Library/Application Support/Nagi`: `config/profiles`, `config/rules`, `config/settings.yaml`, `config/subscriptions.yaml`, `runtime/mihomo.sock`, `runtime/mihomo.pid`, `runtime/mihomo.lock`, `runtime/logs/mihomo.log`, and `cache/subscriptions`. On Linux, Nagi uses `nagi` under `XDG_CONFIG_HOME`, `XDG_DATA_HOME`, and `XDG_STATE_HOME`. It uses `XDG_RUNTIME_DIR/nagi` for the socket and PID when available, otherwise a runtime directory under its state directory.

The state directory also contains the owner-only `tun-intent` preference written by `tun enable` and `tun disable`; effective configuration generation applies this cross-profile preference before mihomo validation and activation. An enabled preference supplies `tun.enable`, automatic routes, interface detection, strict routing, and UDP/TCP port 53 interception while retaining other TUN fields. An explicit disabled preference supplies `tun.enable: false`; an absent or legacy empty preference leaves profile settings unchanged. Startup, reload, profile activation, and explicit or scheduled subscription application use this same layer, so a feed omitting `tun.enable` cannot disable a saved enabled preference. Source profiles, ordinary overrides, and subscription caches remain unchanged. Activation confirms the actual runtime TUN enable state; mihomo can reject adapter creation despite completing configuration activation. Failed configuration changes use the existing disk and runtime recovery transaction, including the prior runtime TUN settings on both platforms. Recovery PUTs include those prior live settings before activation, even when the recorded image predates a runtime TUN patch. A startup mismatch attempts to stop the newly started engine and reports failure.

User-owned overrides live in `config/overrides/NAME.yaml`, separate from the source profile and subscription cache. For a selected profile with an override, persistent custom rules, a saved selector choice, or a saved TUN preference, Nagi merges YAML mappings recursively except DNS server policy maps, replacing lists and scalar values, validates the result with mihomo `-t --check-json`, and writes `config/profiles/.effective-NAME.yaml` for startup or reload. A DNS replacement marker in the override causes Nagi to replace the source DNS section before merging it; the root-level `nagi-dns-replace` and `nagi-dns-proxy-group` markers are stripped from the effective YAML before mihomo sees it. Keeping the generated file beside the source preserves mihomo's relative path resolution. The source remains the target of import, export, backup, restore, and `config show`. A failed override validation restores the previous override. A failed reload restores disk files. The CLI confirms runtime activation through mihomo's `activation_id`; if the runtime changed, it validates and reactivates the prior running effective snapshot. If confirmation or restoration fails, the error reports that runtime state is uncertain. The helper marks configuration reload errors rejected during request parsing, snapshot preparation, or native restricted-policy validation with the additive response field `not_forwarded: true`. Nagi preserves that evidence as a typed error and returns the rejection without activation polling. The ordinary transaction attempts to restore disk settings; an unchanged prior activation ID does not acquire a pending-activation warning. Once controller forwarding has been attempted, the helper cannot set that flag, including for subsequent DNS synchronization failures. Helpers that omit the flag retain conservative recovery behavior. A PUT whose client request timed out may remain in progress inside mihomo. If its activation ID was never observed, even a later confirmed rollback PUT cannot prove the prior configuration will stay active: the original PUT may complete afterward. Nagi attempts to restore disk settings, reports the activation ID observed during recovery, and treats final runtime state as uncertain. Generated effective files are refreshed before startup and reload; they are not authoritative configuration.

DNS policy commands update that local override. A `dns tun on|off` request that conflicts with an explicit saved TUN preference fails before changing the override; change the preference through `tun enable|disable` with mihomo running first. Primary and bootstrap resolvers use HTTPS DoH only; direct mode binds each primary resolver to `#DIRECT`, while proxy mode binds it to a named non-direct proxy node or configured proxy group, including automatic groups. Bootstrap and proxy-node hostname resolution use an IP-address DoH list bound to `#DIRECT`, with an explicit command option to replace the DNSPod defaults. Direct outbound resolution uses this list in proxy mode and the primary list in direct mode, bound to `#DIRECT`. Keeping bootstrap independent from the bound proxy avoids a resolution cycle when the proxy server is named by hostname. Before generating an effective profile, Nagi checks that bound nodes or groups still exist, since mihomo can otherwise interpret a missing name as a network interface and connect directly. DNS server policy maps replace source maps to avoid retaining a plaintext resolver after a subscription update; local suffix exceptions survive a later `dns set`. Explicit suffix exceptions can use a plaintext IP DNS server and are reported by inspection commands. TUN interception is configured with automatic routes, strict routing, and port 53 hijack; whether OS routing and privileges actually activate it is outside configuration validation. Managed DNS also enables mihomo's optional real-address resolution of proxied TCP destinations at the protocol adapter boundary, so a proxy server does not independently resolve those destinations. Hostnames remain available for routing, group selection, and reporting; internal DNS transports retain their existing semantics. `dns check` inspects the selected configuration and probes the mihomo resolver through its control API. It does not inspect operating-system routes or resolver behavior.

Provider creation also updates the selected profile's local override. The CLI adds an HTTP provider and attaches it to an existing supported group or creates a manual select group with `DIRECT` as its initial choice. Because lists replace source lists, the override stores the entire effective group list; subscription application rebases that snapshot against the new source, retaining local group changes while advancing unchanged source groups. Both explicit and automatic application retain the override. Creation uses the configuration lock, mihomo validation, and the same activation and rollback transaction as other configuration changes. It can save while stopped and never starts the engine or changes routing rules implicitly. Mihomo owns provider cache paths, downloads, node decoding, and native healthchecks. New providers attached to automatic groups inherit the effective group healthcheck URL and configured expected status. After a running reload completes initial provider loading, the CLI requests a native provider healthcheck; check failures leave the saved addition in place and produce no separate output. While stopped, the initial check runs when mihomo loads the provider at startup. Provider removal deletes definitions and group use references from source and override together, validates the resulting effective configuration, and reloads once through the same activation transaction. Groups and rules remain present; validation failures restore both configuration layers. Both UI entry points invoke the CLI and refresh displayed state after the result. The [CLI reference](../reference/cli.md#adding-proxy-providers) defines the input and persistence contract.

`start` records a running intent, validates the selected profile with `mihomo -t --check-json`, takes an exclusive runtime lock, launches mihomo with `-ext-ctl-unix`, writes its PID, and waits for the socket. The runtime directory has mode `0700` and the socket has mode `0600`. No TCP controller is configured by Nagi's default profile. `stop` records a stopped intent, sends SIGTERM and uses SIGKILL after its timeout. A `config.lock` serializes configuration mutations, applies, reloads, lifecycle transitions, managed system proxy commands, and proxy operations that can change saved selections or provider state across CLI processes. User lifecycle commands take the quit lock before the configuration and lifecycle locks; the engine lock remains innermost. `quit` releases the configuration lock while it waits for the login monitor to exit, allowing the monitor's shutdown command to complete. A separate lifecycle lock serializes intent writes, stop, start, restart, monitor recovery, and startup checks. An outer quit lock spans the full quit transaction and serializes concurrent user start, stop, restart, and quit commands. Unexpected exits leave a stale PID marker in `status`; recent logs remain available. The installed login service monitors and restarts mihomo after an unexpected exit only when the persisted intent is running. Successful proxy choices are stored per profile in `config/proxy-selections.json` with mode `0600`. Before startup, Nagi puts saved choices for present `select` groups into mihomo's `default-selected` field in the generated effective profile and disables mihomo's separate selection cache in that generated profile. Static group members, including nested groups, can therefore be selected before DNS and TUN activity begins. A saved provider node may become available only after provider loading; mihomo uses its group fallback until that node appears, and Nagi still retries the choice through the control API after startup. Missing groups and static members remain saved for `proxy restore` inspection. Explicit subscription replacement omits these saved defaults and clears the old choices after activation. `proxy auto` clears an automatic group's fixed node through mihomo and removes that group's saved choice. Native group latency tests clear automatic pins when their handler runs. Nagi reads the selected profile before the request and removes its saved choice only after a successful response, a handler-level measurement timeout, or an observed fixed-to-automatic transition after an ambiguous transport failure. Otherwise it retains the saved choice and reports that the reset is unknown. If persistence fails after the live operation, the command reports that the engine changed and the saved choice remains uncertain. Provider inspection reports only safe metadata and node names; provider updates and healthchecks use mihomo's native API. Provider node delay uses the provider-node healthcheck endpoint. Start, restart, and profile reload attempt to replay choices whose groups and nodes still exist; missing choices remain saved and can be inspected with `proxy restore`. A failed control API replay is reported even if mihomo has started or reloaded; the failure does not stop the running engine.

The optional privileged backend is selected explicitly and stored in `config/engine-backend`. In that mode the user CLI sends lifecycle and allowlisted control requests over an authenticated system helper socket. The helper validates and snapshots the selected effective profile, starts mihomo as root, and keeps its controller and logs private. Nagi fetches recent logs and traffic samples through the helper. The per-user login monitor invokes the same CLI operations and retains the same running/stopped intent. Switching backends requires the outgoing mihomo process to be stopped so that the user and privileged processes cannot coexist under one selected backend.

The helper serves at most 32 accepted connections concurrently, including clients still sending their authenticated request. Additional clients wait in the listener backlog. One delayed mihomo `/traffic` sample therefore does not block process status or ordinary controller snapshots. Lifecycle, configuration activation, proxy selection, latency measurements, provider healthchecks, resolver queries, destination rule tests, and DNS journal operations remain serialized by the runtime handler. Only explicitly classified snapshot GET endpoints release that lock during controller I/O; the controller authorization allowlist and socket ownership checks still apply. A snapshot captures the current child and configuration generation under the lock and checks them again before returning. A stop, child exit, or restart invalidates an earlier result with `stale_controller_response`. Attempted configuration activation also invalidates earlier configuration-dependent snapshots. Traffic counters belong to the process, so neither same-process activation nor ordinary node selection interrupts a traffic sample. Each `/traffic` request still returns one bounded sample through the existing framed protocol. Cancellation closes the listener and accepted sockets, cancels controller I/O, and waits for every connection worker before daemon cleanup stops the engine. DNS journal scans retain their existing transaction lock and may wait for a DNS mutation. The concurrency choice is recorded in [decision 0005](../decisions/0005-helper-concurrency.md).

The macOS helper binds one session UID from its root-owned LaunchDaemon definition and checks peer credentials for every request. It opens only regular, user-owned source files under that UID's Nagi configuration directory using `openat` and no-follow traversal. Relative file references resolve beside the source profile. It copies allowed file provider payloads and proxy TLS files into mode `0600` snapshots within a root-owned mode `0700` home, then checks the rewritten profile with mihomo `-t --check-json --config-policy restricted` before start or reload. The child always starts with `--config-policy restricted`; mihomo owns the protocol, plugin, provider, listener, and nested option allowlist, including provider rechecks after decoding. The helper supplies only an audited controller API and never passes a mutable user path to root mihomo. A reload forwards the caller's validated 32-character lowercase hexadecimal `activation_id` unchanged. Because a timed-out reload can apply later, all snapshots and referenced resources remain until the child exits. If the helper restarts with an unobserved child marker or a live controller socket, it refuses a new start rather than risking a duplicate root process. An administrator must inspect and clear an orphaned process before restarting the helper. The trust split is recorded in [decision 0003](../decisions/0003-restricted-root-configuration.md).

The CLI's control client connects to mihomo's REST API through the Unix Socket for version, configuration, proxy, and connection requests. Profile selection and writes use temporary files, atomic replacement, and a most recent backup. Incoming profile content is validated before activation; invalid old content can be replaced and is preserved as bytes for rollback. Import reloads a running engine only when replacing the selected profile. If reload fails, Nagi restores the previous profile or selection on disk and uses a fresh bounded API recovery context to check activation IDs. It reactivates a validated prior running effective configuration when the runtime changed; an invalid prior configuration is never reported as restored. Selection and subscription application can replace an invalid selected-profile record. Commands that do not need the selected profile remain available for recovery; the [CLI reference](../reference/cli.md) defines reporting and recovery behavior.

Runtime mode has two explicit paths. `mode rule|global|direct` patches the running mihomo configuration and is temporary; profile YAML is unchanged. `mode save MODE` validates and atomically updates the selected profile's local override when present, otherwise its source profile, then uses the same reload path as profile changes. `mode saved` reads the effective persisted value. A failed persistent reload restores the modified file and attempts a confirmed runtime restoration when its activation changed.

`config reload` validates the selected profile's effective configuration before requesting `PUT /configs?force=true`; validation failure prevents an API request. `connections show` locates one connection in a fresh API snapshot, and `connections close`/`close-all` send idempotent DELETE requests. `logs follow` seeks to the current end of the append-only log and polls for complete new lines until cancellation. It does not replay historical lines.

Applying local default settings saves the target profile's prior override and a hash of the applied override in a private restore point beside its override file. Nagi copies runtime settings from the default template while retaining the target source and local override's proxy, group, and business-rule fields. It also retains additive local proxy nodes and `tun.enable` from the target's effective configuration, whether enabled or disabled. The separate persistent subscription chain policy is unaffected by applying or restoring default settings. A target with proxies requires `--dns-proxy GROUP` on its first apply; the recorded group is reused when a later apply omits the option. Only a node-less direct profile keeps the template's DNSPod primary DNS without a binding. For a bound group, Nagi replaces the target's DNS section with a fixed policy: Cloudflare and Google IP-address DoH upstreams bound to the group for primary lookups; DNSPod IP-address DoH bound to `#DIRECT` for bootstrap, proxy-node hostnames, and direct outbound resolution; no fallback or DNS server policy; and `respect-rules` and `direct-nameserver-follow-policy` disabled. The command rejects a missing group or one currently selecting `DIRECT`; later group selection changes follow ordinary mihomo semantics, including a user selecting `DIRECT`. The primary DNS path fails when its configured upstreams cannot answer instead of automatically using DNSPod. A route-generation check in the pinned mihomo resolver detects changes to the selected proxy chain before a DNS query, clears the old DNS cache generation, and resets its upstream clients so reused DoH connections do not stay on the old chain. Config activation also resets resolver connections. Neither event closes existing application connections. Status compares the saved hash with the current override and reports whether a DNS proxy binding is required, the recorded group, and group candidates. Restore validates and activates the prior override through the ordinary profile path, then removes the restore point; if another operation changed the override, restore refuses to replace it. Configuration transactions include the restore point in their snapshots.

Subscription URLs are stored in `subscriptions.yaml` with restricted permissions and excluded from list output; refresh writes a separate cache file. Per-subscription age identities are copied into private regular files under `config/subscription-keys`, with directory mode `0700` and file mode `0600`. For an age-armored response, refresh runs the matching installed mihomo decrypt command with ciphertext on standard input and the identity file path in an argument, bounds plaintext, then performs the ordinary parse and normalization before cache replacement. The user CLI decrypts before any privileged helper configuration snapshot; the helper receives only the resulting profile through its existing restricted path. Decryption failure preserves the previous cache and metadata and reports a redacted error. Refresh parses and normalizes a supported mihomo YAML document before replacing the cache and records optional traffic and expiry metadata from `Subscription-Userinfo`. If the index update fails after cache replacement, refresh restores the old cache or removes a newly created one, and returns any restoration error as well as the original failure. Update compares new and old cache nodes; preview compares cached nodes with the current named profile. Applying replaces the named source profile with the downloaded configuration in subscription order. It retains the named profile's local settings and rebases node/group snapshots against the prior and new source before activation. For existing groups, edited `proxies` and `use` lists apply local membership additions/removals to the incoming source list, preserving subscription order and appending distinct local additions in saved order. This prevents a manual node addition from freezing inherited group members removed by a later subscription. Other list fields retain replacement semantics; a persistent subscription chain policy is retained and regenerated against the replacement source. Nagi removes downloaded controller settings, restricts LAN access and built-in, independent `listeners`, `tunnels`, TUIC, and DNS listener binding to loopback, rejects file-defined or malformed listener fields that cannot be normalized, supplies a mixed port if no HTTP or mixed listener is supplied, and disables mihomo's saved selection replay. It writes and selects the resulting profile, then reloads the running mihomo instance once without Nagi's saved selection replay. After successful activation and managed system proxy synchronization it clears Nagi's saved choices for that profile. The reusable preserving-source apply path uses the same subscription composition and retains saved choices for automatic updates; it does not schedule updates. Custom rules stored separately still affect the effective configuration. If validation or reload fails, Nagi restores the prior profile file and selection. Refresh alone does not alter the active profile. Configuration mutations and lifecycle operations share a cross-process configuration lock. Before an apply Nagi snapshots configuration files and the prior running effective configuration. On failure it restores source, override, selection, saved choices, and generated files, then reactivates the validated prior runtime configuration if the activation ID changed. A timed-out request can still finish after the bounded observation window, including after a rollback PUT has been confirmed; Nagi reports that uncertainty instead of claiming a stable runtime rollback.

Login activation and current engine operation are separate controls. `startup enable` installs a missing login service and otherwise enables the existing definition without reloading an active monitor. `startup disable` changes only future login activation, leaving the current monitor, subscription scheduler, and mihomo running. Linux disables the unit without stopping it; macOS persists the launchd disabled-service preference without unloading the job and reads that preference separately from job activity. Service removal still stops the monitor and engine.

Service definitions are replaced through a temporary file. On installation failure, Nagi attempts to restore the prior file state and reports the outcome without claiming the service manager also rolled back. During uninstall, a failed stop/disable preserves the definition for recovery. A subsequent systemd reload failure is reported even if the definition has already been removed. See the [CLI reference](../reference/cli.md#recovery-and-service-failures) for operational behavior.

The macOS menu bar app invokes a fixed `/usr/local/bin/nagi` path through `Process` with `--json`. It does not read runtime files or contact mihomo itself. On launch it calls `start`, accepting `already_running`, and on Quit it calls `quit` before terminating. Failed startup and cleanup remain visible in the menu. It polls status through short-lived commands and reads one-second mihomo traffic samples through `traffic watch` NDJSON. Stream interruption clears stale rates and triggers reconnection while the engine is running. The app stores only its traffic display choice in UserDefaults. The independent login service remains managed through CLI commands.

The user-mode mihomo process starts in a separate process group from its CLI parent. The terminal menu runs `logs follow` and `traffic watch` in child Nagi processes with an interruptible context. A terminal Ctrl-C cancels the stream and returns to its menu page without signaling mihomo. Lifecycle shutdown still targets the recorded mihomo PID with SIGTERM, followed by SIGKILL after the timeout.

### macOS app refresh and command completion

The app coordinates periodic, menu-open, wake, and operation-triggered reads through one refresh worker. Concurrent requests for the same settings generation share an active pass; additional requested fields are queued for a subsequent pass. A mutation advances the settings generation before and after its CLI command, preventing earlier read results from replacing the command's state. Ordinary read requests during a mutation are queued, while required reads after the command can run before mutation controls are enabled again. The worker keeps CLI reads serial, including queries that acquire the CLI's configuration lock.

The polling loop requests engine status, groups, and runtime settings, then waits five seconds after that request completes. Successful profile and override metadata, subscription metadata, and provider reads can be reused for 30 seconds; login service metadata can be reused for 60 seconds. Failed metadata reads invalidate the cached success time so the next periodic request retries them. A changed current profile forces profile, override, DNS binding, and runtime reads. Clearing provider state when the engine stops or becomes unavailable invalidates its cache. Menu-open requests read all displayed CLI state; waking requests the same full refresh. Sleep and quit cancel the refresh worker and invalidate late results. Waking reconciles configuration changes that completed during sleep.

Mode, proxy selection, TUN, system proxy, and login service commands update the model from their successful results. Proxy selection and automatic selection refresh groups; explicit node/group latency tests, Provider check URL/interval and download-interval mutations, and provider operations refresh groups and providers after success or failure; subscription schedule, test-URL, and key changes refresh subscription metadata. Profile activation refreshes profile and runtime fields, and subscription activation also refreshes subscription metadata. Subscription download flows proceed to apply without an intervening list query. A failed download prevents apply; a failed apply retains the downloaded cache, refreshes subscription metadata, and preserves the operation's failure message. Configuration validation, persistence, activation, and rollback remain CLI responsibilities.

While busy, the app cancels status-menu tracking and detaches the menu from its status item. The menu delegate also rejects opening while busy. Completion or failure reattaches the menu once the operation and its required reads finish. Only root-menu lifecycle callbacks change the tracking state or request menu reads. The entire menu tree remains stable while browsing submenus, including moving from a provider's Test Latency submenu to Update Settings. Refresh results appear on the next root-menu opening; closing a menu does not rebuild the tree during AppKit teardown. The App model and CLI serialize configuration operations.

Traffic samples and cleared traffic counters notify only the status-item renderer; they do not rebuild the menu tree. Settings, engine state, and error changes retain the full model notification so operation results and recovery messages reach the menu. Menu timestamp formatting reuses a parser, display formatter, and validation expression; formatter access is serialized and the display time zone follows each call's local or explicitly supplied zone. User-facing timestamps retain minute precision.

Provider and Subscription update and latency settings share native app-modal panels with a fixed 520-point width and a scrolling content area bounded by the visible screen. The window title identifies the settings page and source name once; the content starts with the controls. The scroll document uses a top-aligned content stack without stretching rows to fill the viewport. Update settings load the saved values directly into the checkbox and interval selector, without repeating current-value or source labels. Latency settings load the saved interval and inheritance choices into their controls without repeating cadence or source labels. The URL field loads the complete saved test URL through `proxy healthcheck show KIND NAME --full-url`; normal CLI inspection still returns origins. Inherited values are previewed by the CLI using the same policy and override layers without writing configuration. Known intervals and URLs remain visible in disabled inputs; differing checkers, unavailable values, and unapplied subscriptions use explicit placeholders. Switching to inherited replaces the current input; switching back to custom edits that displayed value without restoring an earlier input. Empty operation feedback is hidden. Each page initializes and updates only its own controls; in particular, the update page never selects or reads items in the latency-only popups. One modal session remains open through initial reads, independent section saves, and read retries. Update drafts separate automatic downloads from preset/custom positive seconds; Provider restore removes the local download interval through the existing CLI reset. Latency interval and URL drafts independently choose inherited or explicit values, and each section has its own save. The URL draft tracks its complete value separately from its saved baseline, allowing direct edits and disabling unchanged saves. A successful URL save retains its text; its reconciliation read updates only the URL baseline and field, preserving the interval draft. An unavailable Provider URL reset is disabled with an explanation. Session-only baselines disable unchanged saves and preserve unsaved edits in the other section. Invalid input disables its save and displays inline guidance. While a read or save is in flight, controls and all close paths are disabled. A later close asks before discarding unsaved edits. Initial read and save failures stay inline for explicit retry. After a successful mutation, the section records its saved baseline before reading current values. A failed read leaves that section pending reconciliation and blocks another save; its refresh action only repeats the read, retaining other section drafts. The panels invoke the existing CLI operations; validation, persistence, activation, and rollback remain CLI responsibilities.

Ordinary CLI invocations wait for a process exit notification instead of polling. The client drains buffered stdout and stderr before decoding the existing JSON envelope, without waiting for EOF from a detached descendant that inherited a pipe. Stdout and stderr each retain a 1 MiB bound. The command deadline remains 45 seconds; timeout and cancellation terminate the child with SIGTERM, followed by SIGKILL after one second if it remains running. A timeout already observed by the client retains its timeout classification if cancellation arrives during termination. Long-lived traffic and subscription streams also register exits before launching and wait for their readers to finish after that notification.

## Latency observations and check settings

Native macOS automatic-group menus distinguish mihomo's current selection (`now`) from its retained manual preference (`fixed`). When a nonempty preference matches the current selection, the header shows **Fixed: NAME**. When they differ, it shows **Current: NAME** and **Manual preference: NAME (not active)** on separate rows; node checkmarks continue to follow the current selection. An absent or empty preference shows **Automatic: NAME**. These labels describe engine state without changing or clearing the preference. **Restore Automatic Selection** remains available through the existing CLI operation.

The CLI decorates group and provider results with scoped identities and existing mihomo delay histories. Group configuration limits candidate sources; provider tests retain their exact owner. Nested group availability resolves the current selected leaf, with cycles and LoadBalance left without a unique state. Native per-URL alive state distinguishes zero-millisecond success from failure. It selects the newest URL-specific observation, retaining failed observations and their timestamps; unavailable or ambiguous history is explicit. Provider history reads are shared within a group-list response. Selection and measurement operations use undecorated group state so history reads do not become a prerequisite for changing a selection or running a test. Nagi does not schedule a second measurement loop or persist its own history. The [CLI contract](../reference/cli.md#recent-node-measurements) defines the public fields and redaction.

Subscription automatic-check interval and test-URL intent live in the subscription index and follow its persisted profile association, including before first apply. Add and Apply saves optional update interval and test URL with the new record before fetching, while the Provider add flow saves its optional test URL in the same configuration transaction as creation. Effective generation applies these policies to eligible native groups and existing provider check mappings before explicit Provider/group settings. It neither enables disabled checks nor creates absent check mappings. Initial apply stages the association inside the configuration transaction before validation; successful activation records the cache/source metadata. Import detaches the old association before activating imported content. Removal and activation failures use the existing transaction to restore both configuration and subscription metadata. Other interval and test-URL operations read the selected effective profile and write local changes through the ordinary override and activation transaction. Provider download-interval changes use the same transaction but change the native Provider `interval` rather than a check interval; zero disables automatic source pulls in the pinned mihomo version. Explicit group intervals and test URLs use local override metadata defined in the [latency settings reference](../reference/cli.md#automatic-latency-check-intervals), so equal source and local values still preserve deliberate user choices across subscription updates. Effective generation applies those settings after ordinary merging and removes the metadata before engine validation. Absent groups leave dormant settings without resurrecting their definitions. Provider healthcheck mappings merge with existing settings. Reset retains unrelated overrides. A Provider URL reset without a usable source or subscription URL is refused before mutation, avoiding a configuration that disables its native checks. Mihomo owns scheduling, provider task registration, lazy skipping, and measurement execution. The terminal and App expose subscription/Provider update intervals, automatic-check intervals and test URLs, plus contextual manual tests. The terminal also exposes group automatic-check intervals and test URLs; the App leaves group edits to the CLI. Their entry points invoke these CLI operations and display the returned source and scheduling caveats. See [Automatic latency check intervals](../reference/cli.md#automatic-latency-check-intervals).

## Rules and subscription persistence

Nagi stores user-owned rules in a separate mode `0600` `config/rules/PROFILE.yaml` file for each profile. Stored-rule commands resolve the selected profile, and effective generation reads only the named profile's rules. Profiles have independent rule names and entries. The former global `config/rules.yaml` is neither read nor migrated. Removing an unselected profile deletes its rules file with the other profile state through the configuration transaction. The document holds named single rules (`kind: rule`), full-rule bundles (`kind: rules`, with native strings in `items`), and previously imported provider sets (`kind: set`). The selected profile is parsed with enabled entries prepended in saved entry order. A full-rule bundle expands into native strings in its original order, preserving each target and options; sets become inline `nagi-*` rule providers and one generated `RULE-SET` rule. Enable, disable, and remove operate on whole named entries. `rules edit` replaces single-rule contents in place, preserving enabled state and position. `rules update NAME [SOURCE]` refreshes an imported bundle or existing provider set in place, retaining its kind, behavior, target, order and enabled state. New imports/updates save a complete `refresh-source` in the private rules file (absolute for local paths), excluded from JSON; public `source` remains a summary and `can_update` signals availability. Older summary-only records require an explicit source once. Existing set updates accept YAML `payload:` or string lists; bundle updates retain the native `rules:` contract. Parsing/download failure changes no stored state; validation/reload failure uses the existing file restoration path. No periodic source refresh is registered. `rules import NAME SOURCE` accepts only complete native rules and reads a local file or HTTP(S) response as a bounded 8 MiB snapshot and never registers an automatic update source. The import has no format or common target argument; no format detection or conversion occurs. YAML imports extract only the `rules:` list or a top-level string list; referenced `RULE-SET` providers and `SUB-RULE` definitions must exist in the effective profile. Mihomo owns native syntax, dependency validation, and matching. Mihomo supplies typed rule diagnostics for invalid format and missing outbound, sub-rule, or rule-provider references. Its optional `target` field contains the redacted reference name. Nagi consumes this evidence without inferring missing targets from candidate YAML. For a missing outbound in an imported top-level rule, human output shows the one-based candidate rule number and target, followed by the confirmed save/runtime state. Import errors report unchanged saved/runtime state only after successful rules-file restoration and before any activation attempt. Profile overrides and custom rules are combined before mihomo validation. A failed effective configuration validation or runtime reload restores the prior rules file. Subscription refresh and apply write profile data independently and therefore retain this rules file. Subscription preflight preserves effective-configuration composition errors and their localized cause rather than wrapping them as custom-rule conflicts. Chain dependency diagnostics identify the referring resource and missing outbound or provider with URL redaction; verified missing targets in enabled custom rules retain the custom-rule conflict classification. A later profile reload regenerates the effective temporary YAML from the source profile, profile override, and enabled custom rules.

## Request rewrite domain storage

The request rewrite domain library stores private per-profile documents independently under `config/request-rewrite/PROFILE.json`, with a separate per-user CA bundle under `config/request-rewrite/ca/`. Profile removal includes its rewrite document in the ordinary configuration transaction and retains the CA. Configuration snapshot/restore excludes exactly the independent `request-rewrite/ca/` subtree and rejects a symbolic link at that boundary; rewrite profile documents remain covered by rollback. Subscription apply/update preserves local rules, authorization and enabled intent; source YAML never grants consent or enables rewriting. Missing documents start disabled and empty. The domain library, persistent ordinary-UID rewrite service, lifecycle coordinator and public CLI are implemented against the published engine pinned in `engine.lock`. A generation journal and independent supervisor cover CAS activation, confirmed rollback, engine exit, certificate renewal and crash blocking. Lifecycle teardown retains rewrite intent; only explicit rewrite disable changes it. Matching source builds include rewrite v2 and capture protocol 1; ordinary installation/update availability still requires a matching Nagi release. Terminal menu forms use the CLI. Native macOS controls passed compilation, packaging and model/CLI tests, and actual Linux/macOS TUN/helper fixtures passed; manual App interaction, sleep/wake and sustained resource checks remain unverified. See the [verification matrix](../development/request-rewrite-acceptance.md) for evidence and remaining gates. The helper binds rewrite ownership from its authenticated session UID at restricted engine startup; it never receives the user CA private key. See the [request rewrite design](request-rewrite.md#transactions-errors-and-lifecycle) for exact ownership, current implementation boundaries and remaining gates.

## Traffic access and restoration

Nagi reads runtime listener, TUN, and LAN state from mihomo's `/configs` API over its private Unix Socket. TUN and LAN changes use `PATCH /configs` and do not modify the selected profile. When mihomo exposes a `tun.device` name, Nagi checks whether the OS interface exists and is up; this does not verify route ownership. On macOS, the system proxy is separate OS state: Nagi snapshots each active network service's HTTP, HTTPS, and SOCKS proxy settings before changing them and writes a private restore journal under the state directory containing both the baseline and the applied target. Linux system proxy management is unsupported. After a successful effective configuration apply, Nagi updates managed HTTP/HTTPS ports to the active mixed or HTTP listener while retaining the original baseline. External edits to managed services cause a conflict and are left untouched. A process watcher observes the mihomo PID and restores the macOS snapshot after exit; `stop`, `restart`, and a stopped `status` also restore it. The journal remains if restoration fails, so the user can retry with `system-proxy disable`.

macOS TUN DNS management is a separate transaction. It derives endpoints from the active TUN's IPv4 and IPv6 prefixes, confirms that the adapter is up and mihomo DNS is enabled, and snapshots network-service static DNS lists or DHCP state before applying and verifying new values. A durable `tun-dns-restore.json` tracks original, applied, and pending values so partial application or a crash can be compensated. Repeated synchronization preserves the original baseline and incorporates newly discovered services. External edits and missing services are reported without overwriting them; incomplete recovery keeps the journal.

The privileged backend owns this journal in the helper's root-private directory. Fixed authenticated `tun_dns_sync`, `tun_dns_restore`, and `tun_dns_status` operations accept no address or filesystem arguments. The helper obtains targets from its own running engine, synchronizes after configuration changes, reconciles delayed activations, and restores after child exit. The user backend keeps the journal under its state directory and uses a detached process watcher. Lifecycle commands and configuration transactions synchronize DNS, compensate failed changes, and report uncertain recovery. DNS errors do not replace process liveness information. The [system DNS decision](../decisions/0004-macos-tun-dns.md) records the choice over gateway-address route changes.

System proxy settings affect applications that honor the OS HTTP and HTTPS proxy configuration. They do not intercept applications that bypass those settings, arbitrary UDP traffic, or DNS queries made outside those applications. TUN uses mihomo's OS virtual network adapter and automatic routes to cover routed traffic while it runs; actual coverage depends on OS privileges, route precedence, and application behavior. LAN access changes only the proxy listener bind and does not redirect other devices' traffic automatically.

## Startup, stale state, and recheck

Lifecycle operations use the runtime lock and PID marker to distinguish a live process from stale state. `status` reports stale PID and unexpected exit without claiming the engine is usable. `recover` and `startup check` remove stale PID/socket markers only after confirming the PID is no longer alive; they never signal a live process. `startup check` then probes `/version` when the engine is running. On macOS, with a reachable engine and a matching restore journal, it compares current OS proxy settings against both the saved baseline and Nagi's target. Each previously known macOS service is checked separately; a service matching either baseline or target values can be reasserted, while a conflicting value is left untouched. New or missing macOS services and old journals without a target are reported, not modified. The installed per-user launchd Agent or systemd unit keeps a foreground CLI monitor alive. It calls the same check every 30 seconds, starts mihomo after stale-state cleanup or when stopped only when intent is running, and doubles the delay after failures up to five minutes. It leaves a live process alone when `/version` cannot be reached. On service termination the monitor stops the engine without changing intent, so disabling the service stops the engine and later enabling it can resume the prior desired state. `quit` first records a pending quit marker, pauses the current login monitor without disabling next-login startup, restores Nagi-managed system proxy settings on macOS, and stops the engine. After successful cleanup it records a completed quit marker. A fresh login monitor converts that completed marker to running intent; a pending marker remains suppressed if shutdown was interrupted. An explicit stopped intent remains stopped even if the monitor itself restarts. A later `start` records running intent and resumes an enabled but inactive monitor. Manual `startup check` remains non-restarting. The manager's enabled and active state is reported separately from the mihomo process state.

## Diagnostics and security

`diagnostics` performs read-only checks against local paths, executable resolution, profile readability, PID liveness, Unix Socket `/version`, mihomo `/configs`, listener reachability, DNS enablement, listener/controller exposure, and owner-only permissions. It does not read profile contents into the report. URL fields in the report retain at most the origin; paths, queries, fragments, and userinfo are removed for sharing. `diagnostics export` serializes the same redacted report to an owner-only file. The report separates process existence, API reachability, configured listener, and proxy path checks.

Subscription metadata is committed under a persistent cache lock whose inode is outside the configuration tree restored by configuration transactions. Refresh downloads and decrypts without locks, then takes `config.lock` followed by the subscription index lock only for cache/index commit; it rereads the index and rejects a changed subscription generation. This prevents stale HTTP results from overwriting schedule or key changes. A single per-user scheduler host is selected by an advisory runtime lock; the live lock plus a fresh heartbeat determines `scheduler_running`. The foreground `subscription watch` command and installed login monitor use the same host. It wakes at the next due time, polls at least once a minute for schedule changes, and downloads due entries without `config.lock`; cache commit takes `config.lock` then the subscription index lock. Each automatic apply takes `config.lock`, rechecks current selection, association, generation, schedule, source hash, and cache version, then uses the ordinary rollback transaction. Other subscriptions update cache only. Source edits or unreadable sources persistently pause automatic activation until explicit apply, even if the old source bytes later return. Downloads continue on schedule during a pause; download errors retain their own failure stage and reason beside `pause_reason`, and every attempt advances `next_due` to the next interval or retry time. The scheduler constructs its backend, control client, and reload store under `config.lock` after checking the current profile and subscription version, preventing a backend switch from activating through a stale client. Candidate source content is combined with that profile's local override and custom rules before rule-target validation; other profiles' rules do not participate. Known inline-provider nodes can satisfy targets, while remote-provider node names are left to mihomo validation. For saved choices, a successful mihomo group response is authoritative; when it is unavailable, Nagi uses effective-profile groups and retains a choice for a group using remote providers because its runtime nodes are unknown. Removed known choices are pruned. A failed apply retains the downloaded cache for retry.

## Proxy nodes, chains, and Tailscale identity

The implementation requires the matching engine pinned in `engine.lock`. Node queries, group membership queries, chain summaries, and dry-run plans read selected-profile configuration while the engine is stopped. Ordinary results contain redacted node metadata, group classification, chain names, and edge changes; full proxy definitions remain private configuration. The [CLI reference](../reference/cli.md#proxy-nodes-and-chains) defines commands, limits, and JSON fields.

Node mutations update the ordinary local override. Adding a Tailscale node with several groups prepares its node and complete explicit membership set together before one validation and save. Group reports separate explicit, automatically included, excluded, and available groups using the effective group configuration. Group changes alter explicit `proxies` entries without changing automatic inclusion or selecting a node. Provider payload nodes are outside top-level node management. Node removal checks effective node, group, provider, DNS, and managed-policy references before the candidate reaches mihomo validation.

A chain's `via` array follows traffic order from first hop to last hop, followed by its target. Nagi emits native `dialer-proxy` edges, explicitly clears the first hop's dialer, and uses provider `override.dialer-proxy` without changing its download proxy. Explicit empty provider overrides take precedence over inherited values. Plan generation reports all edge replacements, shared uses, and conflicts without writing. Commit rejects conflicts and validates the complete dependency graph, including groups and providers. Clearing node/provider targets removes only their incoming edges, retaining other upstream segments. Subscription clearing restores its unmanaged source/override baseline, and previews report the actual restored edges. Multi-target operations prepare one candidate, save once, and request one candidate activation.

Provider-node chains store private `nagi-provider-chain-members` metadata in the ordinary override, retaining source provider, effective node identity, raw-name mapping, protocol, dialer, and outlet intent. They do not snapshot source URLs or credentials. Effective generation derives an exact raw-name-filtered native provider from the current original source definition and uses a native select bridge with `REJECT` empty fallback. Original providers are unchanged, generated providers are excluded from original include-all-provider expansion, and Nagi validates the resulting dependency graph. Provider Tailscale nodes are unsupported because cloning their native adapters could duplicate state and identity. Native provider parsing, fetching, refresh scheduling, routing, and forwarding remain mihomo responsibilities.

An independent provider-node exit creates a readable outlet appended to manual selectors using its source; intermediates remain internal. Generation never selects the outlet. Before activation, ordinary override mutations diff saved outlet identities and clear choices for removed outlets only; reload failure restores those choices alongside the override, and the outer configuration transaction restores runtime/files. Disconnection retains upstream segments still referenced by another chain/outlet and removes unused derived resources. Inspection reads the logical configuration before native generation so source filter/name changes do not prevent listing or disconnecting saved unavailable members. Candidate discovery reads local inline/file/cache evidence only and preserves source order; it does not fetch. For a running privileged backend, a narrow authenticated helper operation accepts only profile, provider name, and a SHA-256 fingerprint of that provider’s complete logical definition. The helper binds those fingerprints to the source configuration before resource rewriting, and reads only the selected provider in its confirmed active root snapshot. It projects raw names and protocols; node definitions, URLs, keys and credentials never cross this interface. Root reads use the existing no-follow, regular-file, owner and 8 MiB checks confined to the helper’s private directory. The CLI applies the existing source filter/rename logic and intersects identities with the current mihomo provider list, retaining source order. Forwarded reloads invalidate evidence before controller access; only a successful response binds the new generation, so an uncertain activation remains unavailable. Stopped inspection falls back to user-readable payload/cache evidence and never reads a root-only cache. File/HTTP initial no-match uses the bridge's `REJECT`; inline no-match fails native configuration validation. A failed native refresh can retain the last accepted node, rather than switching identity. Explicit source update attempts each related derived refresh after source success, reporting any dependent failure. Nagi adds no background provider refresh service.

Derived HTTP payloads use private profile-scoped `profiles/.chain-cache/PROFILE/` resources. Materialization prepares directories `0700` and files `0600`, rejects symlinks, and cleans newly prepared resources on failure. Configuration transaction snapshots include these caches so activation failure restores the previous accepted payload. Successful override replacement/clear and profile removal clean only unreferenced managed cache paths. Read-only plans do not prepare cache resources. The privileged helper accepts only the exact generated user cache mapping and removes its HTTP `path` before ordinary policy validation and snapshot creation; it never opens that user cache. Restricted mihomo rejects every explicit HTTP cache path and manages root-private URL-hashed caches with directories `0700` and files `0600`. Original and derived providers with the same URL share raw payload bytes while retaining independent native filters, overrides, and dialer edges. These native caches follow the ordinary engine cache lifecycle and are not deleted on chain clear or generation cleanup, because the original provider may still use them. Other snapshotted resources retain the existing failure, uncertain reload, and child-exit cleanup behavior. Ordinary restricted validation still rejects arbitrary HTTP-provider paths. Raw configuration, payload caches, and explicitly viewed/exported logs may contain secrets; normal chain output contains identities and redacted metadata only.

Whole-subscription version 1 policies retain static top-level definitions, so combining them with provider-node chains is explicitly refused in either direction. Existing whole-provider dialer semantics remain unchanged.


The profile-local managed policy lives at `config/overrides/PROFILE.yaml.chain-subscription.yaml`. Version `1` stores `subscription`, ordered `via` names, matching ordered `nodes` containing complete sensitive definitions, optional `source-nodes` for source-collision checks, and optional `replaced-edges` for precisely adopted source relationships. Unsupported versions fail explicitly. The former `PROFILE.yaml.tailscale-subscription.yaml` format is unsupported whenever present; Nagi provides no automatic migration or compatibility policy wrapper. Policy files and generated configurations are owner-only. Configuration snapshots and rollback include the complete policy; ordinary output does not serialize it.

Effective generation merges the source and ordinary override, retains policy hop definitions, applies ordered chain edges to eligible effective top-level nodes and every effective provider, then applies the remaining profile layers. Chain members are excluded from targets. Generic `nagi-proxy-additions` metadata retains local definitions, including WireGuard and SOCKS5, and is stripped before engine validation. Source collisions, protected external dialers, unresolved dependencies, and cycles reject the entire candidate. Explicit and scheduled apply replay the same policy over new feed entries and local additions. Neither policy edits nor replay change source/cache bytes; the scheduler continues to compare actual source hashes, and failed candidates remain pending.

Setting subscription scope requires the actual applied subscription-to-profile association and a matching source hash, and does not fetch or apply implicitly. Managed edges cannot be changed individually. Editing a managed Tailscale node updates its retained definition. Clearing or switching the policy materializes retired hop definitions as ordinary additions so later subscription application retains them. Clearing ordinary overrides removes ordinary additions but leaves the separate policy active. Profile import detaches the policy and subscription association transactionally; profile removal includes policy cleanup. Subscription removal refuses an active policy until its chain is cleared. Local defaults preserve business nodes, groups, additions, and policy state.

Mutations use the shared configuration lock, private effective configuration validation, activation IDs, and rollback transaction. Save or activation failure restores the whole previous configuration and attempts bounded runtime recovery; a recovery that cannot be confirmed is reported as uncertain. A stopped engine stays stopped. Auth Keys enter through visible terminal paste, bounded stdin, or private regular-file input before configuration locks. Menu submissions use a private stdin reader, keeping credentials out of argv and avoiding standalone key files. Explicit raw configuration and log viewing/export may expose sensitive values. No configuration operation verifies authenticated forwarding as an implicit prerequisite.

Managed user-mode identity state lives under `config/.tailscale-state`, keyed by profile, node, and normalized control service. Configuration snapshots and rollback exclude this precise subtree, while other configuration files remain covered. Ordinary node deletion and process restart retain identity state.

Before creating a privileged configuration snapshot, the helper rewrites every top-level Tailscale `state-dir` into its own UID-isolated private `.tailscale-state` subtree. Its stable identifier includes normalized configuration identity, node, and control service. Directories are root-owned and mode `0700`; symbolic links and boundary escapes are rejected. The helper never copies user-owned identities or follows a user-specified root write path. Mihomo independently enforces restricted state paths and rejects Tailscale nodes produced by providers, including remote payloads. Snapshot cleanup does not remove persistent identity state.

The user and root backends use separate identities. Backend switching does not migrate them and may need a reusable or new Auth Key. Mihomo synchronously closes old top-level Tailscale instances before replacement activation and serializes Start/Close. Exit-node forwarding waits for login and exit preferences; initialization failure returns an error. A successful Nagi activation records configuration completion, not tailnet readiness. Reload can interrupt established Tailscale connections. The [state decision](../decisions/0006-privileged-tailscale-state.md) records the trust and lifecycle trade-offs.
