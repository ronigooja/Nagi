# Runtime and configuration design

This document describes the implemented process and configuration flow. The CLI is the only control layer used by the macOS app.

On macOS, data lives under `~/Library/Application Support/Nagi`: `config/profiles`, `config/settings.yaml`, `config/subscriptions.yaml`, `runtime/mihomo.sock`, `runtime/mihomo.pid`, `runtime/mihomo.lock`, `runtime/logs/mihomo.log`, and `cache/subscriptions`. On Linux, Nagi uses `nagi` under `XDG_CONFIG_HOME`, `XDG_DATA_HOME`, and `XDG_STATE_HOME`. It uses `XDG_RUNTIME_DIR/nagi` for the socket and PID when available, otherwise a runtime directory under its state directory.

User-owned overrides live in `config/overrides/NAME.yaml`, separate from the source profile and subscription cache. For a selected profile with an override, Nagi merges YAML mappings recursively except DNS server policy maps, replacing lists and scalar values, validates the result with mihomo, and writes `config/profiles/.effective-NAME.yaml` for startup or reload. Keeping the generated file beside the source preserves mihomo's relative path resolution. The source remains the target of import, export, backup, restore, and `config show`. A failed override validation restores the previous override. A failed reload restores the previous override or source selection, while the engine state after a failed API request remains uncertain. Generated effective files are refreshed before startup and reload; they are not authoritative configuration.

DNS policy commands update that local override. Primary and bootstrap resolvers use HTTPS DoH only; direct mode connects directly, while proxy mode binds each primary resolver to a named non-direct proxy node. Before generating an effective profile, Nagi checks that pinned nodes still exist, since mihomo can otherwise interpret a missing name as a network interface and connect directly. DNS server policy maps replace source maps to avoid retaining a plaintext resolver after a subscription update. Explicit suffix exceptions can use a plaintext IP DNS server and are reported by inspection commands. TUN interception is configured with automatic routes, strict routing, and port 53 hijack; whether OS routing and privileges actually activate it is outside configuration validation. `dns check` inspects the selected configuration and probes the mihomo resolver through its control API. It does not inspect operating-system routes or resolver behavior.

`start` records a running intent, validates the selected profile with `mihomo -t`, takes an exclusive runtime lock, launches mihomo with `-ext-ctl-unix`, writes its PID, and waits for the socket. The runtime directory has mode `0700` and the socket has mode `0600`. No TCP controller is configured by Nagi's default profile. `stop` records a stopped intent, sends SIGTERM and uses SIGKILL after its timeout. A separate lifecycle lock serializes intent writes, stop, start, restart, monitor recovery, and startup checks. An outer quit lock spans the full quit transaction and serializes concurrent user start, stop, restart, and quit commands; the monitor uses only the lifecycle lock so service-manager shutdown can wait for monitor cleanup without deadlock. Unexpected exits leave a stale PID marker in `status`; recent logs remain available. The installed login service monitors and restarts mihomo after an unexpected exit only when the persisted intent is running. Successful proxy choices are stored per profile in `config/proxy-selections.json` with mode `0600`. Start, restart, and profile reload attempt to replay choices whose groups and nodes still exist; missing choices remain saved and can be inspected with `proxy restore`.

The optional privileged backend is selected explicitly and stored in `config/engine-backend`. In that mode the user CLI sends lifecycle and allowlisted control requests over an authenticated system helper socket. The helper validates and snapshots the selected effective profile, starts mihomo as root, and keeps its controller and logs private. Nagi fetches recent logs and traffic samples through the helper. The per-user login monitor invokes the same CLI operations and retains the same running/stopped intent. Switching backends requires the outgoing mihomo process to be stopped so that the user and privileged processes cannot coexist under one selected backend.

The macOS helper binds one session UID from its root-owned LaunchDaemon definition and checks peer credentials for every request. It only accepts configurations owned by that UID under the UID's Nagi configuration directory, then writes a root-only snapshot for mihomo. If the helper restarts with an unobserved child marker or a live controller socket, it refuses a new start rather than risking a duplicate root process. An administrator must inspect and clear an orphaned process before restarting the helper.

The CLI's control client connects to mihomo's REST API through the Unix Socket for version, configuration, proxy, and connection requests. Profile selection and writes use temporary files, atomic replacement, and a most recent backup. Incoming profile content is validated before activation; invalid old content can be replaced and is preserved as bytes for rollback. Import reloads a running engine only when replacing the selected profile. If reload fails, Nagi restores the previous profile or selection on disk; this does not prove the engine's state after a failed API request. Selection and subscription application can replace an invalid selected-profile record. Commands that do not need the selected profile remain available for recovery; the [CLI reference](../reference/cli.md) defines reporting and recovery behavior.

Runtime mode has two explicit paths. `mode rule|global|direct` patches the running mihomo configuration and is temporary; profile YAML is unchanged. `mode save MODE` validates and atomically updates the selected profile's local override when present, otherwise its source profile, then uses the same reload path as profile changes. `mode saved` reads the effective persisted value. A failed persistent reload restores the modified file, while a failed mihomo API request cannot prove the prior in-memory state.

`config reload` validates the selected profile's effective configuration before requesting `PUT /configs?force=true`; validation failure prevents an API request. `connections show` locates one connection in a fresh API snapshot, and `connections close`/`close-all` send idempotent DELETE requests. `logs follow` seeks to the current end of the append-only log and polls for complete new lines until cancellation. It does not replay historical lines.

Subscription URLs are stored in `subscriptions.yaml` with restricted permissions and excluded from list output; refresh writes a separate cache file. Refresh parses a supported mihomo YAML document before replacing the cache and records optional traffic and expiry metadata from `Subscription-Userinfo`. If the index update fails after cache replacement, refresh restores the old cache or removes a newly created one, and returns any restoration error as well as the original failure. Update compares new and old cache nodes; preview compares cached nodes with the current named profile. Applying parses the mihomo YAML cache, uses downloaded settings when present, retains prior settings only where the download has no value, and keeps valid proxy-group ordering. Nagi removes downloaded controller settings, restricts LAN access and listener binding to loopback, and supplies a mixed port if no HTTP or mixed listener remains. It writes and selects the resulting profile, then reloads the running mihomo instance once. It attempts to reselect available live proxy-group choices after a successful reload. If validation or reload fails, Nagi restores the prior profile file and selection. Refresh alone does not alter the active profile. These operations use atomic file replacement and rollback within a command; they do not provide transactions across concurrent CLI invocations.

Service definitions are replaced through a temporary file. On installation failure, Nagi attempts to restore the prior file state and reports the outcome without claiming the service manager also rolled back. During uninstall, a failed stop/disable preserves the definition for recovery. A subsequent systemd reload failure is reported even if the definition has already been removed. See the [CLI reference](../reference/cli.md#recovery-and-service-failures) for operational behavior.

The macOS menu bar app invokes a fixed `/usr/local/bin/nagi` path through `Process` with `--json`. It does not read runtime files or contact mihomo itself. On launch it calls `start`, accepting `already_running`, and on Quit it calls `quit` before terminating. Failed startup and cleanup remain visible in the menu. It polls status through short-lived commands and reads one-second mihomo traffic samples through `traffic watch` NDJSON. Stream interruption clears stale rates and triggers reconnection while the engine is running. The app stores only its traffic display choice in UserDefaults. The independent login service remains managed through CLI commands.

## Rules and subscription persistence

Nagi stores user-owned rules in a separate mode `0600` `rules.yaml` file. The selected profile is parsed with this document's enabled rules prepended; imported sets become inline `nagi-*` rule providers. Profile overrides and custom rules are combined before mihomo validation. A failed effective configuration validation or runtime reload restores the prior rules file. Subscription refresh and apply write profile data independently and therefore retain this rules file. A later profile reload regenerates the effective temporary YAML from the source profile, profile override, and enabled custom rules.

## Traffic access and restoration

Nagi reads runtime listener, TUN, and LAN state from mihomo's `/configs` API over its private Unix Socket. TUN and LAN changes use `PATCH /configs` and do not modify the selected profile. When mihomo exposes a `tun.device` name, Nagi checks whether the OS interface exists and is up; this does not verify route ownership. The system proxy is separate OS state: Nagi snapshots it before changing it and writes a private restore journal under the state directory containing both the baseline and the applied target. On macOS the snapshot covers each active network service's HTTP, HTTPS, and SOCKS proxy settings. On Linux it covers GNOME's proxy mode and those proxy endpoints. A process watcher observes the mihomo PID and restores the snapshot after exit; `stop`, `restart`, and a stopped `status` also restore it. The journal remains if restoration fails, so the user can retry with `system-proxy disable`.

System proxy settings affect applications that honor the OS HTTP and HTTPS proxy configuration. They do not intercept applications that bypass those settings, arbitrary UDP traffic, or DNS queries made outside those applications. TUN uses mihomo's OS virtual network adapter and automatic routes to cover routed traffic while it runs; actual coverage depends on OS privileges, route precedence, and application behavior. LAN access changes only the proxy listener bind and does not redirect other devices' traffic automatically.

## Startup, stale state, and recheck

Lifecycle operations use the runtime lock and PID marker to distinguish a live process from stale state. `status` reports stale PID and unexpected exit without claiming the engine is usable. `recover` and `startup check` remove stale PID/socket markers only after confirming the PID is no longer alive; they never signal a live process. `startup check` then probes `/version` when the engine is running. With a reachable engine and a matching restore journal, it compares current OS proxy settings against both the saved baseline and Nagi's target. GNOME settings are reasserted only when the complete mode and endpoints match the baseline. Each previously known macOS service is checked separately; a service matching either baseline or target values can be reasserted, while a conflicting value is left untouched. New or missing macOS services and old journals without a target are reported, not modified. The installed per-user launchd Agent or systemd unit keeps a foreground CLI monitor alive. It calls the same check every 30 seconds, starts mihomo after stale-state cleanup or when stopped only when intent is running, and doubles the delay after failures up to five minutes. It leaves a live process alone when `/version` cannot be reached. On service termination the monitor stops the engine without changing intent, so disabling the service stops the engine and later enabling it can resume the prior desired state. `quit` first records a pending quit marker, pauses the current login monitor without disabling next-login startup, restores Nagi-managed system proxy settings, and stops the engine. After successful cleanup it records a completed quit marker. A fresh login monitor converts that completed marker to running intent; a pending marker remains suppressed if shutdown was interrupted. An explicit stopped intent remains stopped even if the monitor itself restarts. A later `start` records running intent and resumes an enabled but inactive monitor. Manual `startup check` remains non-restarting. The manager's enabled and active state is reported separately from the mihomo process state.

## Diagnostics and security

`diagnostics` performs read-only checks against local paths, executable resolution, profile readability, PID liveness, Unix Socket `/version`, mihomo `/configs`, listener reachability, DNS enablement, listener/controller exposure, and owner-only permissions. It does not read profile contents into the report. `diagnostics export` serializes the same redacted report to an owner-only file. The report separates process existence, API reachability, configured listener, and proxy path checks.
